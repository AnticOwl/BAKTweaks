## Cheat Engine Batman freeze table: exact writer and behavior

The user supplied the `AK_Batman_Freeze_Collection_v1.0.CT` reference table on 2026-10-25. Its scripts and the user's test notes establish the following:

- `01 - Freeze all bone rotations (experimental)` scans for the unique byte sequence `43 0F 29 34 01 0F 57 D7 43 0F 29 54 01 10` and NOPs its first five bytes. In the installed Steam executable this is exactly RVA `+0x328AC4`, instruction `movaps [r9+r8],xmm6`.
- Static disassembly places `+0x328AC4` inside helper `+0x3288A0`. At the store, `r8` is the `SpaceBases` output data pointer and `r9` is a bone byte offset (bone index times 0x20). The next instruction writes the other 16 bytes of the FBoneAtom at `+0x328ACC`, so the NOP blocks quaternion/rotation output while translation output continues. The user reports that this froze Batman's body with a slight residual oscillation, consistent with translation continuing.
- `02 - Freeze Head bone 7` hooks the same instruction. It computes `boneIndex = r9 >> 5`, captures the first `xmm6` quaternion when index 7 is encountered, and, while its freeze flag is on, writes that quaternion back to `[r8+r9]` then skips the original rotation store. The user reports the body kept animating while Head bone 7 stayed still. This is a tested per-bone quaternion override at the actual SpaceBases writer.
- The table's descriptions call the all-rotation entry experimental and the Head entry a tested concept; the user independently reports the results above. The CE script does not freeze LocalAtoms or bone translations.
- `03 - Freeze LocalAtoms Head [7]` is not present in the supplied v1.0 table. The user reports a separate test at `BatmanAK.exe+0x2F732C`, the LocalAtoms writer; it did not visually hold the head still. The static instruction at `+0x2F732C` writes LocalAtoms (`component+0x404`), so it is a different, upstream/input buffer from the component-space SpaceBases output.
- The linked ChatGPT history (“Vérifier les bones Arkham”) independently reports the same Batman results: full-rotation freeze at `+0x328AC4` with slight residual motion, and Head [7] freeze while the rest of the body continued animating. It also says the supplied v1.0 CT was newly assembled from those known routines and had **not** yet been retested as a combined table at that point. Treat the user's original tests as evidence for the routines, but the consolidated table itself as a separate integration that needs its own validation.
- The shared chat records the prior bone-tool sequence: AKBones v0.9 scanner, then LocalAtoms/SpaceBases exploration, RefSkeleton resolver, Head [7]/Eyes [47/48] resolution, and full 297-bone mapping. The user has now supplied the readable `AK_Bones_Organized_Table_v1.1_LISIBLE.lua`, preserved with the CT in `experiments/pose-writer/references/`. The share text names earlier scripts (AKBones v0.9–v1.3 and Pose Snapshot v1.0) but does not provide their source contents. The runtime resolver's next historical checkpoint was a stability test for RSI before continuing with manipulation. Preserve these as recovery targets; don't recreate their claimed functionality from names alone.
